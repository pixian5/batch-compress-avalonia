## 二、P0 致命问题（均为实测验证）

### P0-1 压缩引擎找不到，所有功能实际不可用

- 代码位置：`BatchCompress/ViewModels/MainWindowViewModel.cs:621`、`:674` 硬编码 `FileName = "7z"`。
- 本机实测：

```
command -v 7z   →  MISSING        # 本机没有 7z，Homebrew 只提供 7zz
/opt/homebrew/bin/7zz  → 7-Zip (z) 26.03 (arm64)
/opt/homebrew/bin/rar  → RAR 7.23 (Trial version)
env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin command -v 7z 7zz rar  →  均找不到
```

- 两个问题叠加：
  1. Homebrew 的 `sevenzip` 只安装 `7zz`，**没有名为 `7z` 的可执行文件**，即使 PATH 正确也会失败；
  2. 从 Finder / `/Applications` 启动的 .app 只继承 `PATH=/usr/bin:/bin:/usr/sbin:/sbin`，**不包含 `/opt/homebrew/bin`** —— 这正是“做成 .app 放进 /Applications 运行”的场景，必然失败。
- 修复方向：新增 `ToolLocator`，按候选绝对路径探测（`/opt/homebrew/bin/7zz`、`/opt/homebrew/bin/7z`、`/usr/local/bin/7z`、`7zz`、`7z`、Windows/Linux 常见路径），启动时做环境自检并在界面提示，允许用户手动指定并持久化。

### P0-2 rar + 不读取 stdout = 永久死锁（已复现）

- 代码位置：`MainWindowViewModel.cs:672-693`（压缩）、`:751-777`（解压）、`:832-858`（测试）均为：
  `RedirectStandardOutput = true` → 全程不读取 → 直接 `process.WaitForExit()`。
- 管道缓冲区写满后子进程阻塞、`WaitForExit` 永不返回。
- 实测复现（完全复刻该调用方式）：

```
222 个文件  → rar 向 stdout 写 26177 字节，正常返回（≈118 字节/文件）
3000 个文件 → 25 秒未退出，判定死锁，手动强杀
```

- 影响：源目录文件数约 500+ 时，点“压缩”界面永久卡在“压缩中…”，且“取消”按钮无法终止（见 P0-3），只能强制退出。
- 备注：7-Zip 在管道下会自动屏蔽进度输出（实测 113MB 目录仅 411 字节），暂时不容易触发；但 rar 必然触发。
- 修复方向：`WaitForExitAsync` + 异步读取 stdout/stderr（`OutputDataReceived`/`ErrorDataReceived` 或并行 `ReadToEndAsync`），并用 `using` 释放进程对象。

### P0-3 取消无法终止子进程

- 代码位置：`MainWindowViewModel.cs:541-545`。
- `Cancel()` 只做 `_cancellationTokenSource.Cancel()`，而循环只在“处理下一个项目前”检查 token（`:576`），**正在运行的 `7z/rar` 进程不会被杀**。
- 另有竞态：`_cancellationTokenSource` 在 `finally` 中被 `Dispose()` 并置 null，`Cancel()` 仍可能访问到已释放对象（`ObjectDisposedException`）。
- 修复方向：持有当前进程句柄，取消时 `process.Kill(entireProcessTree: true)`；用局部 token 变量 + `Interlocked.Exchange` 管理生命周期。

### P0-4 跨线程直接更新 UI 绑定属性

- 代码位置：`MainWindowViewModel.cs:687`（`Logs += ...`）、`:700-701`（`Progress = 100`）等，全部在 `Task.Run` 的后台线程中执行。
- 这些属性直接绑定到 `TextBox` / `ProgressBar`。Avalonia.Base 内部带线程校验（`VerifyAccess`），后台线程写入属于未定义行为：轻则不刷新，重则抛 `Call from invalid thread`。
- 修复方向：所有 UI 状态更新统一经 `Dispatcher.UIThread.Post/InvokeAsync`（或在主线程汇总后一次性提交）。

### P0-5 布局越界，日志框盖住进度条区域

- 代码位置：`BatchCompress/Views/MainWindow.axaml:16-87`：Grid 只定义 5 行（索引 0–4），但日志 `TextBox` 使用 `Grid.Row="5"`。
- Avalonia 源码 `Grid.cs:749` 为 `cell.RowIndex = Math.Min(GetRow(child), DefinitionsV.Count - 1)`，**越界行会被钳制到最后一行**，于是进度区（Row=4）与日志框（Row=5）重叠在同一格，日志框 z-order 更靠后而遮挡状态/进度条。
- 修复方向：Grid 改为 6 行，日志独占 `*` 行，进度区单独一行。

### P0-6 解压/测试时“随机密码”逻辑错误，必然失败

- 代码位置：`MainWindowViewModel.cs:727`（解压）、`:808`（测试）：

```csharp
var password = UseRandomPassword ? GeneratePassword() : Password;   // 解压/测试也走了随机生成
```

- 解压时凭空生成**新的**随机密码去解密，永远不可能成功；随机密码还只写进日志（`:583`），既没落盘也没有复制入口，压缩出来的加密包实际上无从解密。
- 附加问题：`GeneratePassword()`（`:870-875`）用 `new Random()`，连续调用可能撞种子，且 8 位口令熵偏低。
- 修复方向：解压/测试只使用用户输入密码（或从“密码本”查询）；压缩时把随机密码写入归档同目录的 `passwords.txt` 并提供“复制密码”；口令改用 `RandomNumberGenerator`。

## 四、P2 工程质量问题

1. **设置写入 .app 包内部，与“重建 .app 后覆盖 /Applications”工作流直接冲突**
   `MainWindowViewModel.cs:415`、`:442` 使用 `AppDomain.CurrentDomain.BaseDirectory`，即 `/Applications/BatchCompress.app/Contents/MacOS/settings.json`。每次“删旧 .app → 复制新 .app”都会清空配置，且写入包内可能破坏代码签名。
   建议改为 `~/Library/Application Support/BatchCompress/settings.json`（Windows 用 `%APPDATA%`），并在退出时自动保存（当前只靠手动点“保存设置”）。

2. **876 行 ViewModel 无分层**：UI 状态、进程调用、参数拼装、设置读写、密码生成、MD5、日志全部集中在一个类；`Models/` 是空目录。
   建议拆为 `Services/ToolLocator`、`Services/ArchiveService`、`Services/SettingsService`、`Models/*`，ViewModel 只保留 UI 状态与命令。

3. **集合使用 `BindingList` + 手动刷新反模式**：`MainWindowViewModel.cs:51-56` 与 `Views/MainWindow.axaml.cs:22-33`（`RefreshUI` → `InvalidateVisual`）。Avalonia 只识别 `INotifyCollectionChanged`，所以现在靠 `OnPropertyChanged(nameof(CompressionItems))` 整表重建。改用 `ObservableCollection<T>` 后可删除这些 hack。

4. **编译绑定被关闭**：`BatchCompress.csproj:7` 的 `AvaloniaUseCompiledBindingsByDefault=false`，所有绑定走反射，既无编译期检查也无性能收益。建议开启并加 `x:CompileBindings`。

5. **死代码 / 无效依赖**：
   - `SharpCompress 0.42.1`（`csproj:26`）引用后一行未用；
   - `Messages/Messages.cs` 三个消息类无人发送；
   - `ViewLocator` 只对 DataTemplate 导航生效，本项目 MainWindow 是直接 `new` 的，实际不参与；
   - `About()` 把版本信息打到日志而非弹窗（`:379-382`）。

6. **版本号三处不一致**：`About()` 硬编码“版本 1.0”、Info.plist 为 0.0.2、`csproj` 无 `<Version>`。按项目规则（每次 +0.0.1）应集中到 csproj（`<Version>` + `AssemblyInformationalVersion`），打包脚本自动同步 Info.plist。

7. **日志实现粗糙**：循环内 `Logs +=` 属 O(n²) 分配、无长度上限、不自动滚到底部，并把密码明文写入日志。建议改 `ObservableCollection<string>` 或 `StringBuilder` 增量追加、限量、密码打码。

8. **工程化缺失**：无 git 仓库 / 无 .gitignore（`bin`、`obj`、`publish`、`*.app`、`.DS_Store`、`settings.json` 应忽略）/ 无单元测试 / 无 CI / 无打包脚本；`.app` 未签名、无 `.icns`（现用 Avalonia 自带图标）。

9. **格式承诺与授权冲突**：README 宣称支持 rar，本机 rar 为 Trial 版（输出 “Evaluation copy. Please register.”），RAR 为专有格式，分发与长期使用存在授权问题。建议默认隐藏 rar 或标注“实验”。

## 五、推进路线（建议）

### P0：让功能真正可用（一次改完并实测验证）
1. 新增 `ToolLocator`：绝对路径探测 `7zz/7z/rar` + 启动自检提示 + 手动指定；
2. 进程层重写：`WaitForExitAsync` + 双流异步读取 + `using` + 取消即 `Kill(entireProcessTree)`；
3. UI 线程调度：日志/进度统一经 `Dispatcher.UIThread`；
4. 修复布局：Grid 改 6 行，日志独占 `*` 行；
5. 修复“解压使用随机密码”逻辑；随机密码落盘 + 复制按钮；
6. 增加 `IsBusy` + `CanExecute`，忙时禁用按钮。

### P1：补齐核心能力
真实进度（`-bsp1` 解析）、按归档名建子目录解压、文件项也参与解压/测试、gz/bz2/xz 对文件夹自动改走 `.tar.*`、tar.gz 两步解、`SkipCompressed` 用 `-xr!` 真正实现、分卷归档识别（可移植 `Google-compress` 项目已成型的 `ArchiveVolumeResolver` / 首卷判定 / 连续性检查经验）、退出码 1 视为警告、保存路径校验与源去重。

### P2：工程化与体验
目录分层重构（Services/Models）、`ObservableCollection` + 编译绑定、设置迁移到用户目录并自动保存、csproj 统一版本号、`git init` + .gitignore + 中文 commit 推送（pixian5）、打包脚本（`dotnet publish -r osx-arm64` + 组 .app + ad-hoc `codesign` + 拷贝到 `/Applications` + `xattr -dr com.apple.quarantine`）、拖拽导入、xunit 覆盖参数拼装、GitHub Actions 构建校验。

## 六、待决策项（需项目所有者确认）

1. **引擎策略**：是否只保留 `7zz`（免费、稳定、格式多）而移除 rar？可同时消除 Trial 授权问题与那条必现死锁路径。
2. **实现路线**：继续调用 CLI（行为一致、实现简单），还是引入 `SharpCompress` 做纯托管实现（无外部依赖，但 7z 写入能力有限）？若继续走 CLI，建议删除 `SharpCompress` 依赖。
3. **与服务器版的关系**：`Google-compress/batch-compress-master` 已有成熟的分卷解析 / 首卷判定 / 连续性检查规则，是否移植到本机 GUI，甚至让本机版取代服务器壳子？
4. **交互形态**：是否改为“拖拽优先 + 任务队列（每项独立状态/重试/打开输出目录）”？现状是逐个点选、列表项不可编辑。
5. **优先级确认**：先做全部 P0，还是只先修 P0-1（不可用）+ P0-2（死锁）两个最痛点。
